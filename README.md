# Profile Matrix

以矩阵形式管理 VS Code 的配置文件（Profiles）与扩展的对应关系。

VS Code 自带的配置文件功能在「管理扩展与配置文件的对应关系」这件事上很弱：你没法一眼看出某个扩展在哪些配置文件里启用、哪些没装，也没法批量修改。这个扩展把这件事变成一张表。

## 它做什么

一张「扩展 × 配置文件」的表，行是扩展、列是配置文件：

| 格子 | 含义 |
|---|---|
| 蓝色实心 | 在这个配置文件里已启用 |
| 橙色斜纹 | 已安装但被禁用 |
| 空心方框 | 这个配置文件里没装（点一下可加进来） |
| 破折号 | 该扩展是全局共享的，不按配置文件区分 |

**操作**

- **点格子** — 切换启用/禁用；未装的格子点一下就加进这个配置文件
- **再点一次** — 撤销这一项改动
- **右键格子** — 把扩展从某个配置文件里移出
- **点扩展名** — 去应用商店查看该扩展
- **「全局」列的开关** — 切换这个扩展是「全局共享」还是「按配置文件单独管理」。开关打开时，后面的配置列全部失效（因为该扩展在所有配置文件里都一样）

**改动是攒着一起应用的**：所有改动先进入待应用队列，底部会显示「N 项改动待应用」，点「应用」才写盘。写盘前会自动备份，各保留最近 5 份。

## ⚠️ 重要：改动需要完全退出 VS Code 才生效

VS Code 把配置文件数据缓存在主进程内存里，而且不做外部变更检测。**Reload Window（重载窗口）不够**——主进程的缓存不会重建，你的改动还会在下一次写盘时被覆盖。

必须**完全退出 VS Code（所有窗口），再重新打开**。

## ⚠️ 关于实现方式，你应该知道

VS Code **没有**提供任何管理配置文件或启用/禁用扩展的公开 API（相关 API 请求已被官方标记为「不计划实现」）。因此这个扩展直接读写 VS Code 的内部数据文件：

- `globalStorage/storage.json` —— 配置文件注册表（**只读**，绝不写入）
- `profiles/<id>/extensions.json` —— 每个配置文件装了哪些扩展
- `profiles/<id>/globalStorage/state.vscdb` —— 每个配置文件禁用了哪些扩展
- `~/.vscode/extensions/extensions.json` —— 扩展的「全局共享」标记

这意味着：

- **属于官方不支持的用法**，VS Code 升级后内部格式若变动，本扩展可能失效
- 每次写盘前都会自动备份（`<原文件名>.pm-backup-<时间戳>`），出问题可以手动恢复
- 配置文件的新建/删除/重命名**不**由本扩展处理，一律跳转 VS Code 原生界面，因为手写配置文件注册表有导致配置文件数据被删除的风险

如果你不接受这些风险，请不要使用本扩展。

## 环境要求

- VS Code **1.128** 或更高版本
- 依赖 Node 内置的 `node:sqlite` 读取扩展禁用状态；更低版本上该模块不可用，矩阵会降级为只读（看不到「已装但禁用」的状态）

## 命令

| 命令 | 说明 |
|---|---|
| `Profile Matrix: 打开扩展矩阵` | 打开矩阵面板 |

## 已知限制

- 内置配置文件（如 Agents）没有自己的扩展清单，它继承默认配置的，因此它的那一列与默认配置一致
- 扩展的「全局共享」标记是扩展级而非配置文件级的，切换它会影响该扩展在**所有**配置文件里的表现
- 工作区级别的扩展启用状态（`Enable (Workspace)`）不在本扩展的管理范围内

## 开发

```bash
npm install
npm run build     # 构建
npm run check     # 类型检查
npm test          # 运行测试
```

按 F5 启动扩展开发宿主调试。
